### 2.1 The refuter defence rests on ORDER, not only on argument — and that was under-stated

`PREREGISTRATION.md` §11 A5 records a pre-registered refutation condition that fired (dispersion
p = 0.001) and was then declared non-binding. The written defence is the technical argument: a
cluster-robust estimator permits arbitrary within-cluster covariance, so within-parent heterogeneity
cannot contradict it.

**The stronger defence is chronological, and the commit history carries it:**

| commit | date | what it did |
|---|---|---|
| `2818590` | 2026-08-15 | Corrected "KEEP assumes perfect correlation" → assumption-minimal. **Prompted by the owner's argument, on general grounds. No test had been run.** |
| `a94c7c4` | 2026-08-15 | Found the homogeneity criterion invalid (min/max range); replaced it. **Still no valid test result.** |
| `ace8dc8` | 2026-08-15 | Ran the corrected test. It fired. Recorded that the refuter's consequence does not follow. |

**The wrong model was corrected before the test existed, for reasons independent of any result.** The
firing came afterwards. That ordering is what separates "we had the model wrong and fixed it" from
"we saw the result and invented a reason". It is verifiable in `git log` and should be stated in any
write-up that reports the refuter.

**The argument still stands on its own and must remain open to challenge.** If a reader shows that
within-parent heterogeneity does invalidate parent-level clustering, the condition binds and the
decision turns to SPLIT. That is written into A5 and is not hedging.

### 2.2 The threshold rule was tested and rejected — that is stronger than caution

The proposed rule was "use wild cluster bootstrap when a single cluster exceeds 10% of a cell". At
2,000 trials **all three cluster structures are mis-sized**, including one whose largest cluster is
3.7% (rejection 0.064 [0.054, 0.075] against nominal 0.05). There is no dominance threshold below
which the asymptotic test is safe **in this data**.

The rule is therefore unconditional, and the recorded justification is "a threshold was tried and
failed", not "we were being careful". Those are different epistemic claims and the file says which
one applies.

### 2.3 The corpus mix-up, and what it cost

The owner's plan for this round assumed the corpus was `Amazon_Fashion` and that escalating to
`Clothing_Shoes_and_Jewelry` was the next lever. **That escalation happened on 2026-08-08**, forced

**check the run logs before reasoning about which corpus a number came from.** This project has now

### 2.4 Measurement overturned a to-be-written rule four times in one session

Recorded because it is a working-practice finding, not a result:

1. **WCB's rationale** — proposed as "the MDE formula understates under a dominant cluster". Measured:
   formula calibrated at 1.01×. The real reason is coverage (4.1× overrejection).
2. **The dominance threshold** — proposed at 10%. Measured: no threshold works.
3. **Gate attainability** — concluded impossible under KEEP at 3M. Measured at 15M: attainable
   (pending §3.1).
4. **The refuter** — written on a model that was wrong when written.

In every case the intuition pointed at a real problem and attached it to the wrong quantity. **The
sequence "measure, then write the rule" is what caught all four.** The reverse order would have
frozen four wrong rules with confident justifications.

## 3. Open items, ordered by what blocks what

### 3.1 BLOCKING — store-level DEFF and MDE at 15M scale

**Why it blocks:** the gate compares an MDE computed at parent-level clustering (29,420 clusters)
against a λ quoted at store-level clustering. Different units. Store is coarser, so `m_bar` rises,
DEFF rises, MDE worsens.

**Bracketed with existing modules** (no new measurement) — KEEP at 15M, cells
men 8,946/8,269/12,997, women 39,509/11,889/20,626:

| stores per parent | m_bar | MDE @CV 15.3 | MDE @CV 18 | λ_min @CV 18 | verdict vs λ lower bound 0.723 |
|---|---|---|---|---|---|
| 1.00 | 5.67 | 0.186 | 0.218 | 0.725 | **tangent** |
| 0.90 | 6.30 | 0.195 | 0.229 | 0.764 | tangent |
| 0.80 | 7.09 | 0.207 | 0.243 | 0.810 | tangent |
| 0.70 | 8.10 | 0.221 | 0.260 | 0.866 | tangent |
| 0.60 | 9.45 | 0.239 | 0.280 | 0.935 | **fails on the point estimate too** |
| 0.50 | 11.34 | 0.261 | 0.307 | 1.023 | fails |

**The comfortable pass becomes tangent across almost the whole plausible range**, and fails outright
if stores are much coarser than parents. The owner's independent estimate (m_bar ≈ 8, MDE ≈ 0.22,
λ_min ≈ 0.73) lands exactly on the 0.70 row.

**What is needed:** `a5_probe.py` must additionally tally clusters by `store`. It already reads
`store` into its index (`build_index` returns it as the fifth tuple element) but never groups by it.
Add a STORE scenario alongside KEEP/EXCLUDE/SPLIT, re-run at 15M, and report both levels side by side
so which one is operative is unambiguous.

**Note:** `data/processed/parent_store.json` maps only the 83 parents in the labelled sample. It is
not enough for this.

### 3.2 BLOCKING the gate declaration — has the analysis population converged?

3M → 15M moved composition by **10.7 points** (structurally-failing share 23.2% → 11.9%; largest
cluster 19.2% → 8.5%). **If it is still moving, there is no "analysis population" yet and the MDE is
chasing a moving target.**

**What is needed:** run at 30M reviews / 3M items and check whether these stabilise:
mega-listing share, failing-listing share, `m_bar`, CV, and the six gradient cell proportions.

**If they have not stabilised**, the pre-registration must define the analysis population **together
with the indexing depth** — "CSJ, 2019 window, N-review block sample against an M-item index" — rather
than as "CSJ, 2019 window". This project already mistook a prefix for a population once
(`DESIGN.md` §5.13); this is the same error one level up.

**Also to be written into `PREREGISTRATION.md` §4 while doing this:** how the sampling frame is
constructed. Block-sampled across `--spread N` disjoint byte offsets via HTTP range requests, because
the files are time-ordered. That is in `DESIGN.md` §5.13 as a trap but **not** in the
pre-registration as a sampling-frame definition, which is where it belongs.

### 3.3 Outstanding measurement — the refuter that should have been written

**Do parents belonging to the same store show correlated errors?** If yes, parent-level clustering is
too fine and the correct level is store — one level *up*. Partial evidence already points that way:
store-level mean deviation spans +0.25 to +1.45 across sellers
(`docs/phase1b-size-deviation-probe.md` §4c).

This is recorded in `PREREGISTRATION.md` §11 A5 as the correctly-specified condition. It is **not**
yet measured, and it interacts with §3.1: if store is the right level, §3.1's answer is not a
sensitivity but the primary.
